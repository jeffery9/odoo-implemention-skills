# Capability Twin 框架评审（sub-agent 与 agent skills）

> **评审对象**：`agents/` 14 个单元、`skills/` 20 个单元、编排器与执行引擎、能力注册中心、交付模板
> **评审日期**：2026-11-17 ｜ **方式**：静态审计 + 端到端实测（全部结论均有可复现命令支撑）
> **范围外**：`templates/` 之外的业务内容正确性、Odoo 源码分析结论本身的准确性

---

## 0. 总体结论

**框架的「设计文档层」明显优于「执行层」。** 编排器、工作流文档、FDE 对齐说明的写作质量高，
但把单元串起来的那根线——`skills_granted`、注册表寻址、失败判定——是三处断开的。

**一句话**：当前状态是一个**可阅读、不可运行**的框架。它会**空跑 13 个步骤后报告成功**，
且子代理从未真正拿到被授予的技能。

| 维度 | 评分 | 依据 |
|---|---|---|
| 架构设计意图 | **B+** | 6+3+4+N 分层清晰，FDE 边界裁定克制 |
| 编排器实现 | **D** | 端到端实测 6 步全 error，仍返回 `completed` |
| 子代理指令质量 | **D−** | 14 个中 8 个为角色扮演模板，0/6 完备度 |
| 技能实现质量 | **C−** | 8/20 可用，2 个导入即崩，1 个产物错配 |
| 注册与可移植性 | **D** | 34/34 条绝对路径，寻址到错误文件 |
| 文档诚实度 | **C** | 4 处承诺与代码不符 |
| **综合** | **D+** | 骨架可复用，接线需重做 |

## 1. P0 阻断级问题（必须先修，否则框架不可信）

### P0-1 工作流空跑，仍报告成功（假绿）

**实测证据**（在临时目录端到端执行 `supply_side_analysis`）：

```
顶层: status = completed | steps_completed = 6
  step 1 Ecosystem Discovery   -> error   Capability ecosystem-discovery-agent not found
  step 2 Technical Analysis    -> error   Capability technical-analysis-agent not found
  step 3 Function Analysis     -> error   ...
  step 4 Domain Analysis       -> error   ...
  step 5 Business Process      -> error   ...
  step 6 Comprehensive         -> error   ...
```

**根因**：`skills/capability-twin-orchestrator/scripts/main.py:432 / 526 / 633 / 739` 四处
均以 `"steps_completed": len(workflow_steps)` 与 `"status": "completed"` 硬编码返回，
**执行循环从不检查每步 `result.status`**。即使全部子步骤失败或仅返回 `semantic_wait`，
顶层依然宣称完成。

同类假绿：`semantic_wait`（5 个 stub agent 的返回值）与 `pending_instruction`（6 个无实现 agent）
在状态判定上与 `success` 等价。**框架无法区分「做完了」和「只是收到了指令」。**

**影响**：这是 FDE 「证据重于状态」原则的直接反例——框架自己就在用状态冒充证据。

### P0-2 注册表寻址错误，且会静默生成空注册表

`config.py:19` 的 `registry_path: str = "capability_registry.json"` 是 **CWD 相对路径**，
而真实注册表位于 `skills/capability-twin-orchestrator/capability_registry.json`。

**实测**：`CapabilityTwinConfig().get_registry_path()` → `capability_registry.json`
（绝对化后为仓库根，**文件不存在**）。

`CapabilityRegistry._load_registry()` 在文件不存在时不是报错，而是**创建空结构并写盘**
（`scripts/capability_registry.py:46-53`）。后果是：在任意目录启动编排器，
都会就地生成一个空 `capability_registry.json`，随后所有能力查询返回
`"Capability not found"`，而 P0-1 让这个失败看起来像成功。

---

### P0-3 `skills_granted` 全链路丢弃 —— FDE 8 个检查点在运行时无效

三条执行路径逐一实测，`skills_granted` 均未到达子代理：

| 路径 | 实测返回 | `skills_granted` |
|---|---|---|
| prompt agent（无 main.py） | `pending_instruction` + `instruction_file`/`goal` | **被丢弃**（`capability_registry.py:173-183` 只回传 4 个字段） |
| stub agent（25 行 main.py） | `semantic_wait` + 自身 AGENT.md 全文 | **未读取**（不解析 argv） |
| 真实 agent（subprocess） | 参数以 argv 传入 | 子代理自身不消费该字段 |

**直接后果**：上一轮在 8 个评审/质量关节点挂载的 `fde-methodology` **只在路由表与文档里存在**，
不会进入任何子代理的指令集。而执行这些步骤的 8 个 `AGENT.md` 中也**没有任何一份提到 FDE**。

> 结论：FDE 融入流水线目前是**声明式**的，不是**运行态**的。若要生效，必须
> ①在 8 份 AGENT.md 写入检查点义务，或 ②让 `execute_capability` 透传并强制加载 `skills_granted`。

### P0-4 可追溯性双技能「导入即崩」——恰是 FDE 最强对齐点

```
skills/source-traceability/main.py:15   from configuration_manager import get_paths
skills/relationship-analysis/main.py:14 from configuration_manager import get_paths
```

`configuration_manager` 在整个仓库中**不存在**（现有实现叫 `configuration-management/main.py`）。
实测两者直接 `ModuleNotFoundError` 退出。

`docs/FDE-2.0对齐说明.md:100` 把这条链路评为「🟢 全框架最强的对齐点：结论必须回溯到源码物理位置」。
**该评级基于设计意图，运行时并不成立**——Python 层完全不可用，只剩提示词层。

### P0-5 质量门把 Markdown 当 Python 解析

`quality-gate` 实现的是 **Python 代码质量检查**（语法/规范/复杂度/安全），
却被授予步骤 10、12、13——这三步的产物是**分析报告与能力单元（Markdown）**。

**实测**：对 `skills/fde-methodology/SKILL.md` 执行 code_quality 检查：

```
check_result: fail | quality_score: 78
SYNTAX_1: 语法错误: invalid character '（' (U+FF08)
```

**后果**：两份最核心的能力（`fde-methodology`、`source-traceability`）的文档产物会被判不合格。
目前因 P0-1 无人读取结果而未爆，一旦修好状态判定，**所有文档交付会被误拦**。

---

### P0-6 三个 agent 越界写到家目录

`technical-analysis-agent` / `delivery-packager-agent` / `ecosystem-discovery-agent`
的 `main.py` 均使用 `Path(__file__).resolve().parents[3]`。

实测 `parents[3]` = `/Users/jeffery`（应为 `parents[2]` = 仓库根）。
因此 `technical-analysis-agent` 把分片写到 `/Users/jeffery/kb/shards`。

**这解释了为什么仓库内 `kb/` 始终为空**——「知识沉淀」被写到了仓外。
同文件还有 `for f in shard_dir.glob("*.json"): f.unlink()`（无条件清空旧分片），
非幂等、不可并发、会误删他人数据。

## 2. P1 结构与一致性问题

### 2-1 子代理：14 个中只有 3 个有真实实现

| 类型 | 数量 | 单元 | 实测行为 |
|---|---|---|---|
| 有真实实现 | **3** | ecosystem-discovery（88 行）、technical-analysis（78 行）、delivery-packager（35 行） | 真实扫描/落盘 |
| stub（25 行同构） | **5** | business-process、capability-extractor、comprehensive-analysis、domain-analysis、function-analysis | 回显自身 AGENT.md，`semantic_wait` |
| 无任何实现 | **6** | industry-requirements、solution-architect、implementation-guide、human-review-gatekeeper、trustworthiness-auditor、solution-builder-master | `pending_instruction` |

5 个 stub 的 `main.py` 完全同构（仅 `agent_dir.name` 不同），本质是「把提示词再念一遍」。

### 2-2 指令质量：8/14 个 agent 完备度为 0

按「输出契约 / 证据要求 / 完成判据 / 禁止事项 / 示例 / 升级移交」六项扫描：

| 得分 | 单元 |
|---|---|
| 4/6 | delivery-packager、solution-builder-master |
| 3/6 | ecosystem-discovery、technical-analysis、trustworthiness-auditor、human-review-gatekeeper |
| 2/6 | capability-extractor、comprehensive-analysis |
| **0/6** | **business-process、domain-analysis、function-analysis、implementation-guide、industry-requirements、solution-architect** |

0 分组全部是 45–46 行的「角色定义 + 核心职责」模板，例如 solution-architect 的全文实质是
「你是解决方案架构师，负责架构设计」。**这类指令产出的是通用散文，不是可验收交付物。**
反例是 `technical-analysis-agent`（496 行，含扫描策略与证据格式）——证明该团队有能力写好，
只是多数单元没写。

### 2-3 `skills_used` 是复制粘贴，未表达真实依赖

11 个声明了 `skills_used` 的 agent **全部为 `["generic-analyzer", "template-processor"]`**，
包括本应依赖 `quality-gate` + `source-traceability` 的 trustworthiness-auditor，
和本应依赖 `quality-gate` 的 human-review-gatekeeper。**声明与职责无关。**

### 2-4 `business-process-agent` 被当作 skill 授予

编排器步骤 5 的 `skills_granted` 里出现 `"business-process-agent"`——它是 **agent**，不是 skill。
注册表 `skills` 段无此条目，加载必然失败。

### 2-5 4 个单元缺 frontmatter → 注册表出现占位描述

`capability-extractor-agent`、`comprehensive-analysis-agent`、
`enhanced-intent-understanding`、`intent-to-action-mapper` 无 YAML frontmatter。

`discover_capabilities.py:72` 因此回退为 `f"Capability unit: {name}"`。
注册表里 4 条描述是**无信息的占位符**，其中 capability-extractor 是核心能力提取单元。

### 2-6 两个 5 行 SKILL.md（只有元数据，无正文）

`enhanced-intent-understanding`、`intent-to-action-mapper` 的 SKILL.md 只有 frontmatter，
正文为空——而两者各带 395 / 558 行实现。**技能被加载时，模型读到的是零指令。**

### 2-7 注册中心不可移植 + 每次重建全量噪声

- 34/34 条 `path` 为绝对路径（`/Users/jeffery/...`），换机器全部失效。
- `registered_at` 使用 `datetime.now()`，每次重建刷新全部时间戳 → 整文件 diff。
- `capabilities` 字段恒为 `{}`（`scan_*` 从不填充），是一段死结构。
- `allowed_tools` 硬编码为 `["Read","Grep","Glob","Bash"]`，**忽略 frontmatter 的 `allowed-tools`** → 注册表权限与实际权限不一致。

### 2-8 `discover_capabilities.py` 在错误目录下会静默清空注册表

`PROJECT_ROOT = parents[1]` → `/Users/jeffery`，`FRAMEWORK_ROOT = /Users/jeffery/CAPABILITY_TWIN`。
仓库改名或移动后，`AGENTS_DIR` 不存在 → `scan_agents()` 返回 `{}` → `main()` **不报错，直接写空的注册表**。
建议改为仓库相对路径 + 空扫描时 `sys.exit(1)`。

### 2-9 技能之间零组合，「网格」名不副实

34 个 Python 模块中，跨技能 import 只有 2 条（`capability_registry`、`file_operations`）。
其余技能彼此完全隔离。架构图上画的 mesh，在代码层是一堆孤岛，组合全靠 LLM 提示词。
`scripts/ast_analyzer.py`、`odoo_module_graph.py`、`view_aggregator.py` 从未被任何模块引用。

### 2-10 11 个死脚本 / 2 个离群技能

- 死脚本：根目录 `clean_*.py`(3)、`filter_skills.py`、`update_capability_registry.py`、
  `migrate_legacy_knowledge.py`、`render_mrp_deliverables.py`，加 `scripts/` 下 4 个，均零引用。
  其中 `finalize_documentation.py:103` 还引用了**不存在的模板** `STRATEGIC_FUNCTIONAL_SPEC_V6.md`。

> 后续处置（2026-11-19）：上述 11 个死脚本已删除；仍活跃的
> `discover_capabilities.py` 与 `mine_odoo_source.py` 已迁入 `scripts/`，
> 根目录仅保留 pytest 约定要求的 `conftest.py`。本节保留原始评审结论作为历史证据。
- 离群技能：`json-canvas`（643 行）、`obsidian-bases`（619 行）是通用 Obsidian 工具，
  与 Odoo 交付链无关，也未被任何 agent 或流水线引用。合计 1262 行 SKILL.md 属范围蔓延。
- 意图类三技能重叠：`intent-understanding`(443)、`enhanced-intent-understanding`(395)、
  `intent-to-action-mapper`(558)，职责边界未定义，且后两者 SKILL.md 为空。

### 2-11 工程卫生

- **无 `.gitignore`**、无 CI、无 `agents/` 与编排器的任何测试。
- 运行产物入库：`skills/intent-to-action-mapper/capability_twin_runs/` 2 个 run 目录（6 个文件）被提交。
- 测试：8 个 skill 共 **48 个用例通过**；7 个 collection 失败（`No module named 'main'` /
  `configuration_manager`）；`template-processor` 9 项失败（`~/.template_processor_cache` 的
  `FileExistsError` 来自沙箱 shim，**需在非沙箱环境复核**，不宜直接判定为代码缺陷）。

## 5. 修复路线（按投入产出排序）

3. `capability_registry.py:173-183` → 回传 `skills_granted`，并在 prompt agent 分支明确
   「必须加载这些技能」。
4. 3 个 agent 的 `parents[3]` → `parents[2]`；去掉无条件 `unlink()`。

### 第二批：让 FDE 检查点真正生效（约一天）

6. `quality-gate` 增加 `doc_quality` 检查类型，或把步骤 10/12/13 的授予改为

### 第三批：补齐单元质量（约三天）

### 第四批：工程化（持续）

## 6. 一个判断

框架当前最大的风险不是「功能少」，而是**它会把失败报告成成功**。
在 P0-1 与 P0-3 修复之前，任何基于本框架输出的交付物都无法自证「分析真的做过」——
这与 FDE 2.0 §10.4 的可追溯性要求、以及本仓自己写下的「证据重于状态」是直接冲突的。

建议把第一批（4 个文件）作为前置门禁完成，再继续任何能力扩展。
