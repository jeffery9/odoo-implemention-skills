# Capability Twin 项目维护指南

本文件面向**仓库维护者**，回答「改这个仓库时，什么必须同步、怎么验证、怎么发布」。
它不重复 `README.md` 的使用命令，也不替代单个技能包内部的 `MAINTENANCE.md`；三者分工如下：

| 文档 | 读者 | 回答的问题 | 事实源层级 |
|---|---|---|---|
| `README.md` | 使用者 | 框架是什么、怎么调用、怎么安装 | **使用向**技术手册 |
| 本文件 `docs/项目维护指南.md` | 仓库维护者 | 改仓库的哪一处要同步什么、怎么验、怎么发 | 仓库级**维护向**治理事实源 |
| `skills/<name>/MAINTENANCE.md`（如 `odoo-implementation`） | 单包维护者 | 某个技能包的文件职责与变更流程 | 包内事实源，不冲突时服从本文件 |

**职责互斥清单**（写内容前先对照，避免两处重复）：

| 主题 | 归属 | 另一文档的处理 |
|---|---|---|
| 框架定位、工作流概念、CLI 调用、交付模板、安装命令与依赖、运行前提、场景门禁用法 | `README.md` | 本文件不复述调用命令，只引用入口路径 |
| 基线快照、仓库地图、注册表维护契约、变更流程、发布与合并、检查清单、红线、未决项 | 本文件 | README 不自述维护动作，只给指针 |
| 历史维护脚本清单与调用方式 | 本文件 §2 | README §10.5 仅保留一行指针 |
| 单包文件职责与变更流程 | 包内 `MAINTENANCE.md` | 两文档只引用，不复制包内细节 |

判定规则：一段内容若以「使用者该怎么用」开头，归 README；若以「维护者该怎么改/验/发」开头，归本文件。
两文档之间只做指针式引用（`见 <文档> §x`），不复制正文。

**冲突裁决顺序**：代码 > 本文件与包内 MAINTENANCE > `docs/` 下的阶段性方案文档（`*-plan.md`、评审记录）。
文档若与代码不符，以代码为准并把落差登记为缺口（见 `skills/odoo-implementation/TODO.md` 的做法），不得靠改文档掩盖。

**职责边界**

- 业务场景只有一个事实源：`skills/gherkin-bdd/features/<odoo_module>/*.feature`。
  UAT、步骤桩、追溯矩阵均为派生产物，写入 `capability_twin_runs/`，不入库、不复制场景正文。
- 技能资源（模板、feature、`agents/`、注册表）必须放在技能包内部，随 `npx skills` 一起分发；
  运行时产物只能写用户工作区，不得写回技能目录。

### 2.1 `scripts/` 工具脚本分类

`scripts/` 下的仓库级工具**不随技能分发**，按职责分三类。它们曾散落于仓库根，
现统一收口到此处；分类是维护口径，不改变各自的可执行性。

| 类别 | 脚本 | 复用价值与运行条件 |
|---|---|---|
| 活跃工具 | `discover_capabilities.py`、`mine_odoo_source.py`、`check_docs_baseline.py`、`check_ontology.py`、`check_ontology_contract.py` | 日常维护必跑/按需跑；后三者为 CI 守卫（文档基线、本体产物、本体消费闭环），`mine_odoo_source.py` 需 `ODOO_SOURCE_PATH` |
| 通用分析/渲染 | `ast_analyzer.py`、`view_aggregator.py`、`finalize_documentation.py` | 零外部依赖的源码分析能力；渲染器依赖项目侧 snapshot 与模板，缺输入时显式失败 |
| 历史遗留 | `legacy_paths.py`、`clean_*.py`、`filter_skills.py`、`update_capability_registry.py`、`migrate_legacy_knowledge.py`、`render_mrp_deliverables.py` | 服务于早期 CT 交付目录或一次性迁移/演示；路径统一经 `legacy_paths.py` 显式传入，无默认值，默认干跑 |

维护约定：

- 通用工具可独立 CLI 运行；**零引用不等于无价值**，评审记录中的「死脚本」是当时的引用现状，不是删除依据。
- 历史脚本运行必须显式给 `--registry` / `--ct-dir` 或 `CT_LEGACY_*` 环境变量；
  缺失即报错退出，不猜测默认目录，避免误删。
- 新增仓库级工具一律放 `scripts/`，按本文件定位上层资源（`Path(__file__).resolve().parent.parent`），
  不得依赖 CWD 或写死仓库目录名；`tests/test_no_hardcoded_paths.py` 会扫描全仓把关。
- **厂商中立**：工具必须为任意技能容器工作，不绑定某个 agent 厂商的目录名。
  定位同源资源（模板、兄弟技能）时按结构特征搜索（如 `rglob` 匹配
  `template-processor/templates/deliverables`），不以 `.claude` 等具体目录为锚；
  识别历史路径时按 `agents` / `skills` 目录段判定，而非某个容器名。
  例外：安装布局测试用 `.claude/skills` 作**测试夹具**验证通用性，属合法用例；
  `framework_paths.py` 注释中的容器名枚举仅为支持的布局说明。
  `tests/test_script_vendor_neutral.py` 守卫此约定。

## 3. 能力注册表：维护契约

`capability_registry.json` 是编排器寻址的唯一依据，改动技能或 agent 后必须重建：

```bash
# 在仓库根目录执行；脚本按自身位置定位，不依赖 CWD
python3 scripts/discover_capabilities.py
```

重建必须满足以下不变量，任何一条被破坏都应视为回归：

| 不变量 | 说明 |
|---|---|
| 相对路径 | `path` / `file` 为仓库相对路径；出现 `/Users/`、`/home/`、`C:\Users\` 即失败（由 `test_no_hardcoded_paths.py` 守卫） |
| 空扫描中止 | agent/skill 扫描结果为空时脚本应报错退出，不得静默写出空注册表（历史 P0-2 曾静默生成空表） |
| `allowed-tools` 来自 frontmatter | 不得硬编码固定列表，否则注册表权限与实际加载不一致 |
| 版本动态同步 | `version` 从 `SKILL.md` frontmatter 读取；**禁止在守卫测试里硬编码期望版本** |
| `capabilities` 保持空 | 曾用于五层能力链设计，已被否决；由测试锁定为空，防止复活 |
| 重建幂等 | 连续重建哈希一致（`registered_at` 沿用旧值，不刷新时间戳） |

**版本假绿教训（必须记住）**：`test_registry_integration.py::test_04` 曾把 `version` 硬编码为
`0.1.0`，导致 `SKILL.md` 升到 `0.4.0` 而注册表停在 `0.1.0` 时测试仍全绿。
现已改为从 frontmatter 动态读取。**任何"把期望值写死在测试里"的守卫都要警惕同类假绿。**

## 4. 变更流程（按类型）

### 4.1 新增或重构技能 / agent

1. 目录遵循 `skills/<name>/SKILL.md`（agent 为 `.../agents/<name>/AGENT.md`）平铺结构，
   frontmatter 必须含 `name`、`description`、`version`、`allowed-tools`；
   沿用现有字段语义，不改已有技能的 `name` / `description` 原义。
2. 资源（模板、脚本、参考文档）放入该技能包内部，确保 `npx skills` 安装可达。
3. 新建测试放入该技能的 `tests/` 或仓库 `tests/`，全离线（不连真实 Odoo）。
4. **重建注册表**（§3），确认新单元被登记、路径可达。
5. 跑全量 `pytest`，passed 数不得低于基线。

### 4.2 修改编排器 / 工作流

- `6+3+4+N` 的阶段与编号**不可改**；只在既有挂载点追加可选分支，默认关闭。
- 状态判定必须如实：`semantic_wait` / `pending_instruction` 不得计为成功（历史 P0-1：
  空跑仍报 `completed`）。新增返回路径时检查是否绕过了 `_workflow_outcome()` 结算。
- 路径一律经 `framework_paths.py`，不得用固定深度的 `parents[N]`（历史 P0-6：
  `parents[3]` 曾越界写到用户家目录）。
- 业务场景门禁复用 `gherkin-bdd` 引擎；模块无规格时回落基线不算该模块通过
  （`satisfies_module=false`），不得渲染其场景类交付物。

### 4.3 修改契约字段 / 版本

- schema（如 `schemas/odoo-implementation.schema.json`）先改，校验脚本与测试同步；
  领域规则（如 `if/then`）在 schema 与脚本两处保持一致。
- 新增字段必须可选：既有技能无新字段时应判 `skipped`，不是 `error`。
- SKILL.md 版本升级 → 重建注册表 → 确认守卫通过。语义约定见各包 `MAINTENANCE.md`。

### 4.4 修改路径 / 安装布局

- 禁止硬编码绝对路径；Odoo 源码路径只认环境变量 `ODOO_SOURCE_PATH`。
- `skills/capability-twin-orchestrator/tests/test_install_layout.py` 用真实复制布局回归；安装后自检
  `python3 <skills_root>/capability-twin-orchestrator/scripts/framework_paths.py`
  应输出 `layout=install` 且 `templates_source=skill`。

## 5. 发布流程

**红线：禁止直接推送 main。** 所有变更经特性分支 PR 合并。历史惯例如下：

```bash
# 1. 基于最新 main 建特性分支
git checkout -b <type>/<short-name> origin/main

# 2. 提交改动，本地验证（见 §6）

# 3. 推送特性分支——HTTPS 代理历史上多次 502，用 SSH 直连更稳
git push -u git@github.com:<owner>/<repo>.git HEAD:refs/heads/<branch>

# 4. 创建 PR 到 main

# 5. 合并前确认 MERGEABLE/CLEAN 且 head commit 与本地一致，再合并
gh pr merge <N> --merge --match-head-commit <sha>
```

要点：

- `--match-head-commit` 确保只合入已验证的提交；若 head 已被他人更新，命令会拒绝合并。
- 合并方式是 `--merge`（保留 merge commit），不用 squash / rebase，与既有 PR 保持一致。
- GitHub GraphQL 端点偶发 502；若合并请求失败，先查 PR 状态是否仍为 OPEN，
  重试一次通常成功。失败不应被理解为"已合并"。
- 合并后验证远程 main 含全部改动，再把本地 main worktree 快进：
  `git merge --ff-only origin/main`，并在合并后基线重跑全量测试。

## 6. 提交前检查清单

```bash
# 1. 全量回归：passed 数不得低于 §1 基线
python3 -m pytest -q

# 2. 契约校验（若改动了 odoo-implementation）
python3 skills/odoo-implementation/scripts/validate_odoo_manifest.py \
  skills/odoo-implementation/SKILL.md

# 3. 注册表：若新增/改了技能或 agent，重建并检查幂等
python3 scripts/discover_capabilities.py
R=skills/capability-twin-orchestrator/capability_registry.json
H1=$(shasum -a 256 "$R" | cut -d' ' -f1)
python3 scripts/discover_capabilities.py >/dev/null
H2=$(shasum -a 256 "$R" | cut -d' ' -f1)
[ "$H1" = "$H2" ] && echo "幂等 PASS" || echo "幂等 FAIL"

# 4. 场景门禁（若改动了 .feature）
python3 skills/gherkin-bdd/scripts/gherkin_gate.py validate \
  skills/gherkin-bdd/features
```

```bash
# 5. 文档基线守卫（治理 A+：祖先 + 测试数 + 过期词 + 单一事实源）
python3 scripts/check_docs_baseline.py --self-test
python3 scripts/check_docs_baseline.py --test-count "<CI 实测 passed 数>"
```

人工核对：

- 文档中的数字与事实一致（技能/agent 数、版本号、测试数）；测试数只在 §1 出现。
- 新增文件已登记到相应职责矩阵（仓库级见 §2，包级见该包 `MAINTENANCE.md`）。
- 无硬编码路径、无外部框架专有印记（FSCR 等）。
- 对外展示材料（`static/description/index.html`、`__manifest__.py` 的 `description`）
  未出现内部模型名、脚本名、Sprint/SEC 编号、版本迭代史、测试数量等实现术语。

- 本文件随 main 更新，改动走 PR（§5），不直接改 main。
- §1 基线表仅在合并后更新；§8 未决项只放指针，不放细节。
- §1 是测试数与基线提交的唯一可写位置；其它文档只写指针，禁止复制 `N passed`、
  基线哈希或「待 CI 复核/验收」等时态表述。守卫见 `scripts/check_docs_baseline.py`。
- 若与 `README.md` 出现职能重叠，使用向内容留在 README，维护向内容留在本文件。
- 发现文档与代码不符时，以代码为准，并把落差登记到对应 TODO（§8），不要静默改数字了事。
