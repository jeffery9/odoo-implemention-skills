## 1. 结论摘要

按重要性排序，四条结论：

1. **采用「摘要内置」的自包含注入（2026-11-17 同日调整）。** 初版为纯引用式
   （skill 只指向外部文档位置）；应要求改为把 4 组外部引用压缩为
   `skills/fde-methodology/references/` 下的 4 份内置摘要，共 580 行、对应原文 5784 行
   （压缩比 10.0%），使能力单元**离线自包含**。**本仓不再保留任何仓外文档引用**：
   4 份摘要带 `§x.y` 条款号锚点，即该能力单元的全部执行依据。
   这样既与使用向 README 的职能保持分离，也避免产生第二份可漂移的口径。
   本轮产物为**一个能力单元 + 4 份内置摘要 + 一份对齐说明 + 一行 README 入口 + 注册中心重建**。
2. **框架生命周期与 FDE 价值流不是同一层东西，且不应合并。** [F] §6.4 明确
   Value Stream ≠ Project Lifecycle。本框架的 `6+3+4+N` 是**研究与交付引擎的执行结构**，
   价值流七活动是**跨项目的端到端客户价值流**。把 13 步改名为七活动，或把七活动做成
   阶段枚举，才是真正违反基础标准。本轮不改任何阶段名称（§3）。
3. **框架是工程侧引擎，不是 FDE 经营系统。** [M] 的 G0 组合门、G1 立项门与 G3 价值门
   的裁定权分别属于组合负责人、立项评审会、发现负责人 + 客户，均在框架边界之外。
   框架能实质支撑的是 **G2 工程门的证据侧**与 **G4 资产门的记录侧**。因此本轮只注入
   「观察口径与执行纪律」，不新建门禁状态机、不新增业务字段（§4、§5）。
4. **FDE 已融入四条流水线，方式是「检查点挂载」而非「新增阶段」（同日 10:25 追加）。**
   `capability-twin-orchestrator/scripts/main.py` 的四张 `workflow_steps` 路由表在
   8 个评审 / 质量关节点（步骤 2、6、7、9、10、12、13 与 N 步第 4 步）的既有
   `skills_granted` 中追加 `fde-methodology`；运行时 `task_plan.md` 增加
   `FDE Review Checklist` 章节（只引用、不复制 §5 清单）。**步骤编号、步骤名与
   `6+3+4+N` 结构一律不动**，Gap 对标（Phase 3.5）仍只作评审视角；挂载点分布见
   `references/workflows.md` 的 FDE Checkpoints 节与 `SKILL.md` §4.1。

## 3. 三层边界（最容易做错的地方）

| 层次 | 名称 | 取值 | 落点 | 视角 |
|---|---|---|---|---|
| A | FDE 价值流活动（7） | 客户需求 → 发现 → 价值定义 → 方案设计 → 工程与交付 → 采纳与运营 → 价值实现 | **概念层，框架内不建枚举、不做筛选字段** | 客户价值、跨项目 |
| B | 框架研究/交付生命周期 | 6 步供给侧 + 3 步需求侧 + 4 步提取与 QA + N 步 SMP 客制化 | `capability-twin-orchestrator`、`references/workflows.md` | 本引擎的执行结构 |
| C | Odoo 原生能力单元 | 模块 / 模型 / 视图 / 控制流 / 物理行号 | `kb/`、`capability_registry.json` | 源码事实 |

**A 与 B 只有部分重叠，不存在一一对应**：

| B 段 | 与 A 的关系 |
|---|---|
| 供给侧 6 步 | 覆盖「发现 / 方案设计」的**项目内**部分，起点是「模块被选定」，不含客户需求产生 |
| 需求侧 3 步 + Gap 对标 | 覆盖「价值定义」的一部分，但 A 的价值定义可能发生在立项之前 |
| 提取与 QA 4 步 | 对应「工程与交付」主体；交付物是报告/PR 包与审计证据，不是客户采纳 |
| SMP 客制化 N 步 | 属「工程与交付」尾段的迭代 |
| **B 的终点** | 交付包 + 人工复核通过；**A 的「采纳与运营 / 价值实现」在 B 边界之外** |

### 为什么不改 `6+3+4+N`

1. **语义代价**：13 步已被 Agent 网格、`workflows.md`、`deliverables` 模板与
   `kb/logs/` 历史记录引用；改编号或改名会让「第几步产出了什么」的既有语义全体漂移。
2. **概念代价**：把项目/引擎生命周期改名成价值流活动，等于把 A、B 压成一层，
   恰恰违反 [F] §6.4。
3. **术语污染**：`pmp_next` 已经发生过「把执行层五环当成价值流五阶段」的两册互相
   污染事故；跨仓沿用同一组名词会重演该问题。

**落地纪律**：价值流在本框架内是**观察口径与评审视角**，不是记录上的状态字段；
不引入七阶段枚举、不把七阶段做成可筛选字段、不把 B 的阶段编号写成 A 的活动名。

## 5. 刻意不做（[I] 判断，登记备查）

对齐不等于把标准每句话都变成框架里的字段或文件。以下六类本轮明确不做：

| 项 | 不做的理由 |
|---|---|
| 成熟度 L1–L6 分级（[F] §18.2） | 标准自述为 "a maturity framework, not mandatory organizational stages"；做成字段等于给框架打无观测证据的分，且留出刷等级空间 |
| AI 作为倍增器（[F] §13） | 是关于 AI 作用的论断，不是可观测事实；框架已有的采矿线程数、命中数属产出数据，不该改名为「乘数」 |
| 增值/浪费分类、八类浪费（[F] §7.2–7.3） | 定性工作坊框架；做成标签会增加录入负担，且贴标签者正是被评价者 |
| 商业模型枚举（[F] §12.5） | 报价、合同、结算在框架边界外，无结算口径可挂 |
| G0–G4 门禁状态机与「价值流七阶段」枚举 | 前者裁定权属人且属经营层，后者违反 §6.4；两者都会造出无消费点的第二套事实 |
| 加权总分、个人/方案排名、自动写判断值 | [F] §9.5 / §16.3 防博弈；沿用 `pmp_next` 的 L-1a 纪律：系统不代填由人裁定的值，回流只给只读建议，消费方主动采用才落库 |

> 补充（10:25）：检查点挂载**复用既有 `skills_granted` 数组**，不是新增字段、不是门禁
> 状态机、也不是价值流阶段枚举，因此不违反上表任何一条。检查清单本身仍是
> `fde-methodology/SKILL.md` §5 的唯一一份，`task_plan.md` 只引用不复刻。

## 6. 剩余缺口与验证欠账

| 编号 | 事项 | 性质 | 建议顺序 |
|---|---|---|---|
| **A-1** | 交付物模板缺价值三态（基线 / 目标 / 实测）与「交付验收 ≠ 价值实现」的边界声明 | 模板缺口，本轮不改模板 | 优先：在 `GAP_ANALYSIS_REPORT.md` / `HANDOVER_MANIFEST.md` 增说明级小节，不新增必填字段 |
| **A-2** | 人工复核门未区分工程质量与业务质量，无「两门不得互相替代」判据 | 门禁缺口 | 其次：在 `quality-gate` 与 `human-review-gatekeeper-agent` 的判据中分别列出两类证据 |
| **A-3** | 学习与资产回流无消费点（`kb/` 只写不读回决策） | 结构缺口，同 `pmp_next` L-1 | 先定口径（灌到哪、谁确认、如何防评分被优化），再谈自动回流 |
| **A-4** | 流动度量无事实源（无价值事件、无打点日期、无跨项目标识） | **真实数据缺口**，非代码缺口 | 不实现指标；在采集到真实事件前，任何 Lead Time / TTV 数字都不可跨批次比较 |
| **A-5** | 能力单元复用缺「适用边界 + 验证证据 + 版本」的强制元数据 | 模板缺口 | 在 `CAPABILITY_UNIT_SPEC.md` 复用章节补三项，与 `SKILL.md` §5.8 一致 |

> ⚠ A-3 与 A-4 的区分沿用 2026-11-06 `pmp_next` 复核结论：**「数据的有无」不是代码缺口，
> 「消费点的有无」是**。没有消费点，数据来了也无处可去；没有事实源，指标来了也是
> 精确到天、实际上不存在的数字。

**A 级提升结论（2026-11-27）**：
- **A-1 已解决**：`GAP_ANALYSIS_REPORT.md` / `HANDOVER_MANIFEST.md` 已加入价值三态与
  「交付验收 ≠ 价值实现」说明级小节（不新增必填字段）。
- **A-2 已解决**：`quality-gate` 在报告中标注 `quality_dimension`（只产工程侧证据），
  `human-review-gatekeeper-agent` 明确双维分列且不得互相替代。
- **A-3 已解决**：`knowledge-manager retrieve(..., approved_only=true)` 是回流消费点，
  只消费带 `approved_by` + `source_anchor` 的候选；`capability-extractor-agent` 承担消费义务。
- **A-4 维持不做**：无价值事件、打点日期与跨项目标识，不实现 Lead Time / TTV；
  在采集到真实事件前，「—」不得改为 0，也不得跨批次比较。
- **A-5 已解决**：`CAPABILITY_UNIT_SPEC.md` 复用章节加入适用边界、验证证据与版本三项。

## 7. 维护约定

1. 框架新增「价值流 / 度量」类能力时，先查 §3 三层边界；不要把七活动写进
   `workflows.md` 的阶段编号，也不要把 `6+3+4+N` 改名。
2. 新增或修改任何度量，必须同步写出口径定义（起点 / 完成 / 边界 / 排除 / 警告），
   否则会出现「有数字、没定义」的不可比数据（[F] §9.2 明令禁止）。
3. 「—」不得改成 0；不做加权总分、不做排名、不自动写由人判定的值。
4. 上游标准更新时先复核 §2 层级，按 **[F] → [M] → how → [REF]** 顺序重生成 4 份摘要，
   再更新 `SKILL.md` 条款号与本文；**禁止只改 SKILL.md 而不同步摘要**，否则会产生
   两份互相漂移的下游口径。不得用本仓口径反推上游定义。
5. 摘要必须保留条款号锚点；新增内容一律先压缩为内置摘要并登记来源与行数，
   再在 `SKILL.md` §8 的摘要索引中登记，不得重新引入仓外路径引用。
6. §6 的缺口被解决时，须在本节登记「已解决 / 维持不做」及理由，避免重复评审。
7. 编排器 `main.py` 的路由表新增或调整阶段时，同步复核 `SKILL.md` §4.1 挂载点、
   `workflows.md` 的 FDE Checkpoints 节与 `task_plan.md` 模板；检查点不得写成新阶段编号，
   也不得把价值流七活动做成阶段枚举。
