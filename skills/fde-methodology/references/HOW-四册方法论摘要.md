## 1. Portfolio Management（组合管理）

**六项核心原则（§2）**：Value First（不是金额排行榜）· Dual Flow（价值流动 vs 工作流动，
工作完成 ≠ 价值实现）· Flow over Utilization（不以 100% 利用率为目标）·
Evidence over Status（不以 CRM 阶段/颜色/主观百分比代替事实）· Reversible Decisions
（不确定时优先付费 Discovery 而非一次性固定总价）· Learning over Repetition（复用须经验证、
授权与适用性判断）。

**对象与术语（§3）**：Opportunity / Discovery Engagement / Project / Portfolio /
Resource Pool / Value Stream / Work Stream。**「项目」是商业与责任边界，「价值流」是价值创造路径，
「工作流」是工作执行路径——三者不可用同一个 stage 字段表达。**

- **机会生命周期（§4）**：`NEW → QUALIFYING → DISCOVERY → EVALUATING → APPROVED/HOLD/REJECTED`；
  Discovery 必须有预算上限、时间边界、交付物、待验证假设、结束决策，结论为
  `GO / ITERATE / HOLD / NO-GO`。状态只表达管理阶段，**不代替决策记录**。
- **硬门槛（§5.1）六条**：客户业务负责人、价值主张可定义可验证、合规安全有控制、
  关键技术/数据风险已验证或有 Discovery 计划、预算现金流合同可接受、关键资源存在或可行替代。
  **评分只用于排序，不可覆盖硬门槛**（§5.2）；决策输出六要素：决策、依据、承诺、条件、
  责任人、复审触发器（§5.3）。
- **容量（§6）**：`可承诺容量 = 可用工时 − 已承诺工作 − 休假/维护 − 风险缓冲`；
  七类 WIP（Opportunity / Project / Value-stage / DEV / Ready-for-UAT / QA / Rework）；
  共享 QA 容量必须单独呈现，**不能让 DEV 自行宣布 UAT 通过来消除 QA 队列**。
- **指标（§7）**：经济（合同额/确认收入/开票/回款分列；`EAC = AC + ETC`）与流动
  （价值流 Lead Time、采用率、业务结果达成率；工作流 Cycle/Active/Waiting/Blocked Time、
  WIP、吞吐、返工率）。定义时间指标必须统一起止事件；**指标用于发现系统性约束，不用于孤立评价个人**。
- **止损与退出（§9）**：客户长期不供数据/人员、技术路径证伪、基准或归因不成立、EAC 恶化、
  资源长期不可得、范围严重偏离、客户不采用 → **重新评估而非自动追加资源**。
- **Odoo 落地边界（§11）**：优先复用 CRM、`project.project`、工时、费用、会计与盈利模型；
  上层组合模型只承载跨项目决策信息，**不得成为第二套任务系统、工时系统或总账**。

## 2. 立项评估方法论（发现与评估）

- **五维评估（§2）** 与「从人天到价值」的立论（§1）：价值主张、价值流动、成本模型、报价模型、
  决策规则；九张工作表构成价值与成本的统一数据骨架（§7）。
- **十三条口径纪律（§8，违反即阻断）**：
  1 合同金额 ≠ 确认收入 ≠ 开票 ≠ 收款；2 未完项目并排显示实际与预计完工；3 内部成本费率与
  对客计费费率分开；4 AI 费用不重复收费；5 分摊成本不重复计入直接成本；6 未采用的 AI 输出
  仍是已发生成本；7 基准成本为零时节省率**无定义**；8 风险准备金是预算安排不是实际成本；
  9 收益分享不得重复计算（同一价值不二次变现）；10 业务价值 ≠ 可分享收益（须过四道门）；
  11 不同收益类别不能简单相加；12 低毛利必须例外审批并记录原因；13 返工必须记录原因与责任。
- **立项十问（§9.1）**：问题真实 / 业务负责人 / 预算付款 / 范围可估算 / 技术与数据风险 /
  验收条件 / 现场部署或持续运营 / 资产复用机会 / 战略匹配 / 利润达标。答不出者进风险清单，
  **不默认「不会出问题」**。
- **模式附加确认**：固定总价须范围可控、变更机制、验收可执行、准备金合理（§9.2）；
  结果激励须基准可靠、指标可测、归因合理、客户供数、外部因素处理、财务转换、结算周期、
  激励上限、不重复收费，**条件不满足就不应作为基础商业模式**（§9.3）。
- **止损触发（§9.4）**：EAC 超预算、范围扩大、客户资源缺失、技术验证失败、AI 成本超预期、
  返工率异常、验收条件变化、付款延迟、毛利低于下限 → 管理评审。**止损 ≠ 放弃客户。**
- **反例 8（§9.5，最关键）**：**上线 ≠ 验收 ≠ 价值实现**。三件事分开记：① 工程完成
  （代码/配置/自动化测试、PR 合并）② 验收（独立 UAT 通过 + 业务验收签字）③ 价值实现
  （业务指标四道门核验，可能验收后数月）。立项阶段就要把 ②③ 的责任人、判据、观察窗口写进合同；
  **报告里不许出现不带主语和判据的「已交付」**。
- **输出物（§10）**：价值主张卡、价值阶段范围、价值流动图、验收责任落点、任务估算表、
  五桶预算、报价试算、风险清单、十问答卷、收益与价值口径预置。

## 3. Sprint 执行方法论（工程执行）

**两条架构原则（高于本文其余章节，冲突时以本节为准）**：

1. **双流模型（§架构原则一）**：价值流动（诊断→设计→建设→部署→运营/改善→价值验证）与
   工作流动（待办→承诺→进行中→工程完成→待 UAT→UAT 中→验收→收口）**不共享一个混合状态字段**。
   铁律：价值流动决定工作为什么存在；**工作完成不等于价值实现**。一个价值阶段通常横跨多个
   Sprint，一个 Sprint 也可服务多个价值阶段，**不做一对一绑定**；`sp_stage` 是推进环节
   （问题→能力→结果→资产→分享），**不是价值阶段**。
2. **双质量门禁（§架构原则二）**：工程门（单 DEV：代码/配置、单元与集成测试、自动化测试、
   可测试版本、PR 合并）与 UAT 门（共享 QA：独立执行、场景覆盖、结果留痕、缺陷关闭或例外、
   QA 记录结论）。`DoD = 工程门 ∧ UAT 门`，**不压缩成一个 Done**；DEV 不能自行宣布 UAT 通过。

**七条操作性原则（§架构原则表）**：Value First / Dual Flow / Evidence over Status /
Single DEV Ownership / Independent UAT / Flow over Utilization / Learning over Repetition。
> 第 6 条的真实含义：瓶颈在 QA 时，让 DEV 多产出只会把库存堆在队列里——**库存不是吞吐**。

**五层 DoD（§4，分层不合并）**：Task DoD、**Engineering DoD**、**UAT Acceptance**
（前两层才是 Sprint 收口条件）／ Business Acceptance（客户）／ Value Realization（观察期后业务指标）。
后三层属价值流动，**不能被 Sprint Done 顶替，也不拖住 Sprint**。

**证据（§13）**：五类——Engineering（PR、评审、测试、CI）/ Deployment（部署、版本、环境、
回滚）/ **UAT（共享 QA）** / Business（使用数据、指标快照）/ Acceptance·Financial。
最小要求：每条证据能回答「证明什么、来自哪里、关联哪个版本/任务/验收项、谁产生、何时产生、
是否有效」。**优先引用既有事实来源，不为每类证据再造一套手工文档；证据索引不能变成第二个事实系统**；
截图不能替代可重复测试结果，会议纪要不是 DoD 证据。

## 4. 组织学习与资产管理（组织学习与资产）

- **学习闭环（§2）**：项目执行事实（工时/成本/周期/返工、工程门与 UAT 结果、客户采用与价值验证、
  资产创建与复用）→ 项目结束与阶段分析 → 知识提炼与资产评审 → 资产库/标准工时/估算参数/模板
  → 下一轮 Portfolio 与立项评估 → 新项目执行。学习**贯穿全生命周期**，不只结项时总结。
- **七类资产（§3，按用途而非文件类型）**：Engineering / AI / Data / Domain / Delivery /
  Knowledge / Measurement Asset。**客户专属数据、商业秘密、未授权代码与个人信息不得因「复用」
  进入通用资产库。**
- **生命周期（§4）**：`CANDIDATE → REVIEW → VALIDATED → PUBLISHED → DEPRECATED/RETIRED`。
  Validated 必须记录支持版本、适用条件、**不适用边界**、测试证据、已知限制、维护策略；
  Published 必须有版本、Owner、授权范围、使用说明；退役保留历史引用，不静默删除。
- **复用记录与价值（§6）**：每次复用记录资产及版本、项目、场景、采用/修改/放弃结果、
  实际工时、从零开发基准、适配成本、缺陷与维护成本、复用确认人。
  `Gross Reuse Saving = Baseline Effort − Actual Reuse Effort`；
  `Net = Gross − Adaptation Cost − Incremental Maintenance Cost`。
  **基准必须可比；无可信基准时只能记录复用事实，不得宣称确定节省金额**（与 [F] §9.2 同纪律）。
  复用价值分类（工程效率、周期、质量、客户业务价值、维护成本、获客报价优势）**不能简单相加**，
  须与项目毛利、收益分享统一口径，防止重复计价。
- **反馈（§7、§12）**：标准成本与估算按实际偏差校准；Portfolio 与立项消费复用收益与能力差距，
  改善机会排序与未来报价。

## 5. 四册共同纪律（[I] 提炼，供本框架直接复用）

1. **不造第二套事实**：优先复用既有记录、原生对象与原始证据；证据索引只引用，不另立事实系统。
2. **三层不混用**：价值阶段 / 工作状态 / 执行环节不用同一个 stage 字段表达；不做一对一绑定。
3. **无定义不显示 0**：基准为零时比率无定义；无可信基准时只记录事实，不宣称节省。
4. **判断值由人写**：系统可提示、可预填草稿、可拦门，但不代填由人裁定的结论。
5. **交付验收与价值实现分轨**，且价值裁定独立于交付方。
