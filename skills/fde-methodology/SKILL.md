## 1. When to Use

- 评审 `6+3+4+N` 任一阶段的产出物（分析报告、Gap 方案、Capability Unit、PR 交付包）。
- 判断「分析完成 / 方案交付」能否被当作「客户价值已实现」。
- 复用能力单元、生成交接包、写入 KB 长期事实前的适用性检查。
- 引入任何流动度量、评分、成熟度或阶段枚举前，检查是否会造成术语污染或第二套事实。
- 编排器执行 `6+3+4+N` 任一流水线时，在挂载检查点（见 §4.1）按本清单复核。
- 需要一份可追溯的 FDE 条款号引用时（评审记录、验收证据）——先读内置摘要定位条款。

When NOT to use：

- 只需执行源码白盒挖掘、语法校验、模板渲染等纯技术动作。
- 需要**逐字引用标准全文**（本能力单元只提供压缩摘要，不覆盖全文）。
- 需要给组织打成熟度等级、给方案打加权总分或做个人排名——这些是本框架明确**不做**的事。

## 2. 必须保持的口径（引用，不改写）

**三流**（[F] §4）：价值流 / 工作流 / 知识与资产流；彼此独立、相互强化。
资产流是组织学习机制，**不是另一条客户价值流**。

**四子系统**（[F] §5、§14）：组合管理、发现与评估、工程执行、组织学习与资产。
主循环：选择机会 → 验证价值 → 执行工程 → 实现客户价值 → 捕获学习 → 改进未来决策。

**价值流七活动**（[F] §6.2）：客户需求 → 发现 → 价值定义 → 方案设计 →
工程与交付 → 采纳与运营 → 价值实现。**价值流 ≠ 项目生命周期**（§6.4），
一条价值流可跨多个项目，一个项目可只改善其中一段。

**五道门禁**（[M] §11.2）：G0 组合门 / G1 立项门 / G2 工程门 / G3 价值门 / G4 资产门。
一条铁律：**价值由独立于交付方的人用基线对照裁定，不由交付方自证**（§11.1 注④、§13）。

**双维质量**（[F] §15）：工程质量门与价值质量门互补，任一门不能替代另一门。

**基本指标**（[F] §9.1，表列 9 项；上游行文称「八个基础指标」）：Lead Time、Process Time、
Waiting Time、Flow Efficiency、WIP、Throughput、Rework Rate、Time to Value、
Value Realization Rate。
硬要求：定义与数字同屏（§9.2）；TTV ≠ Lead Time（§9.3）；流动效率分子分母同边界（§9.4）；
不做加权总分、不做排名（§9.5 / §16.3）。

**十四原则**（[F] §17）：价值优先、客户情境、先问题后方案、成果重于产出、端到端思维、
流动重于利用率、拉动重于推动、证据重于状态、双维质量、持续改进、
复用而不丢失情境、AI 作为倍增器、经济可持续性、组织学习。

## 3. 三层边界（本框架最容易做错的地方）

| 层次 | 名称 | 取值 | 落点 | 视角 |
|---|---|---|---|---|
| A | FDE 价值流活动（7） | 见 §2 | **概念层，不在本框架建枚举、不做筛选字段** | 客户价值、跨项目 |
| B | 框架研究/交付生命周期 | 6 步供给侧 + 3 步需求侧 + 4 步提取交付 + N 步 SMP 客制化 | `capability-twin-orchestrator` / README | 本框架的执行结构 |
| C | Odoo 原生能力单元 | 模块 / 模型 / 视图 / 控制流 | `kb/` + `capability_registry.json` | 源码事实 |

**A 与 B 不存在一一对应**，只有部分重叠：B 的供给侧研究覆盖 A 的「发现 / 方案设计」的
**项目内**部分；B 的需求侧对齐覆盖「价值定义」的一部分；B 的提取交付对应
「工程与交付」主体；A 的「采纳与运营 / 价值实现」在 B 的边界**之外**。
B 的 6/3/4/N 是**工作量与阶段编号**，不是价值流阶段，**不得改名为七活动**。

落地纪律：
1. 不新增「价值流七阶段」枚举、字段、筛选器或状态机。
2. 不把 B 的阶段编号写成 A 的活动名，反之亦然。
3. 价值流在本框架内是**观察口径与评审视角**，不是记录上的状态字段。

## 5. 执行检查清单（每次评审必须逐条过）

1. **先问题后方案**：输入是否含具体客户问题与业务负责人？缺则标注 `Discovery 待验证`，
   不以合同金额、模块热度或分析完成度代替价值真实性（[F] 原则三，组合册 §4.1）。
2. **价值可证伪**：是否写出基线 / 目标 / 实测三态与测量来源？「价值实现」不等于
   「方案已交付」（[F] §5.4–5.5）。无基线时如实写「无基线」，不编造数字。
3. **证据重于状态**：每条结论是否可回溯到 Odoo 源码物理位置或可核验材料？
   以「已完成 / 已通过」代替证据，视为未通过（[F] 原则八）。
4. **双维质量分离**：工程质量证据与业务质量证据分别列示；不得用工程质量门
   的结论宣布价值实现（[F] §15.2、[M] §11.1）。
5. **定义与数字同屏**：出现任何时间/比率指标，同时给出起点事件、完成事件、
   边界、时间基准、排除项与警告；代理起点必须显式声明 `is_proxy`（[F] §9.2）；
   Lead Time 报 P50 与 P90（[M] §2.5）。
6. **无定义显示「—」**：分母为 0、事件缺失、日期倒序一律返回无定义，**不显示 0**；
   未核验项不进价值实现率分母。
7. **不做总分与排名**：不做加权总分、不做成熟度等级、不做个人排名；
   允许方向性平衡提示（[F] §9.5 / §16.3）。
8. **复用不丢情境**：Capability Unit 复用必须带来源、适用边界、版本与验证证据；
   不自动写入由人判定的结论值（L-1a 纪律），回流只给**只读建议**，消费方主动采用才落库。
9. **不造第二套事实**：优先复用 `kb/` 与 `capability_registry.json` 既有记录，
   不为对齐 FDE 新增一套并行登记、评分或状态字段。

## 6. 输出契约

使用本能力单元做评审时，输出应包含：

- 检查清单 1–9 的逐条结论（通过 / 不通过 / 不适用 + 依据）。
- 引用的 FDE 条款号与层级标注（[F] / [M] / [I] 判断）。
- 缺口清单：区分「真实数据缺口」「代码/模板缺口」「刻意不做」，不给空泛建议。
- 明确声明本次评审是否为**只读**，是否改动了被评审文件。

## 7. 禁止事项（Anti-patterns）

- 把七活动写成框架枚举、把 6+3+4+N 改名为价值流阶段。
- 把成熟度 L1–L6、AI 乘数、浪费分类、商业模型扩展做成字段或评分。
- 把交付包生成、UAT 脚本通过写成「价值已实现」。
- 用「—」之外的方式掩盖无定义的指标；用 0 冒充无数据。
- 自动填写由人裁定的判断值（价值裁定、门禁结论、机会评分、根因与措施）。
- **凭内置摘要改写上游定义**，或在框架内复制上游标准**全文**
  （仅允许带条款号锚点的压缩摘要）。
- 把 [REF] 先例里的模型字段、门禁代码、报表行直接搬进本框架（见先例摘要 §7）。

## 9. 维护约定

1. 上游发布新版本时，先核对 §0 层级，**按 [F] → [M] → how → [REF] 顺序
   重生成对应摘要并复核条款号**，再更新本文件；不得用本仓文件反推上游定义。
2. 框架新增「价值流 / 度量」类能力时，先查 §3 三层边界。
3. 新增或修改任何度量，必须同时补齐口径定义，否则视为「有数字、没定义」的不可比数据。
4. 本文件、`docs/FDE-2.0对齐说明.md` 与 4 份摘要必须同版本演进：
   对齐说明记录判断，本文件记录执行，摘要记录压缩后的标准口径。
5. 摘要必须保留条款号锚点；**禁止只改 SKILL.md 而不同步摘要**，
   否则会产生两份互相漂移的下游口径；新增内容一律先压缩为内置摘要，
   不得重新引入仓外路径引用。
6. 编排器路由表新增或调整阶段时，同步复核 §4.1 挂载点与 `workflows.md` 的
   FDE Checkpoints 节；不得把检查点写成新阶段编号，也不得把价值流七活动做成阶段枚举。
